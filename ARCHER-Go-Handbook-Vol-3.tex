\hypertarget{preface-volume-3}{%
\subsection{Preface --- Volume 3}\label{preface-volume-3}}

A distributed system needs surfaces: interfaces through which clients
interact, channels through which events propagate, and protocols through
which services coordinate. Volume 3 builds all three for the ARCHER
platform.

The REST API chapter constructs a production-grade HTTP server using
Go's standard library --- method-based routing, a composable middleware
chain (request ID, logging, recovery, Prometheus), typed JSON
encode/decode with rich error classification, health and readiness
probes for Kubernetes, and the full graceful drain sequence. This is not
a framework tutorial. It is a systems engineering chapter about how HTTP
servers fail, how timeouts prevent resource exhaustion, and how
middleware communicates context across handler boundaries.

The WebSocket chapter implements the Hub pattern --- Go's idiomatic
solution for managing concurrent long-lived connections without mutex
contention. One goroutine owns the subscriber map; all others
communicate through channels. Read pumps detect disconnection; write
pumps batch outbound messages; ping/pong tickers detect silent dead
connections. The chapter connects this hub to the ARCHER telemetry
pipeline for live dashboard delivery.

The Kafka chapter addresses the fundamental throughput mismatch in
telemetry systems: a load generator producing 50,000 metric events per
second cannot write directly to a database at that rate. Kafka is the
durable buffer that absorbs production speed and delivers at consumption
speed. The chapter covers producer batching, consumer group semantics,
at-least-once delivery, manual offset commit, and the Dead Letter Queue
pattern for permanent failures.

The Docker chapter closes the volume with the deployment reality: Go
services don't live on developer laptops. Every binary built in Volumes
1--3 must be packaged in a minimal container, aligned with cgroup CPU
and memory limits, and integrated with the Kubernetes pod lifecycle.

\hypertarget{the-standard-library-first-principle}{%
\subsection{1. The Standard Library First
Principle}\label{the-standard-library-first-principle}}

Go's \texttt{net/http} package is production-ready without a framework.
Major production systems --- Docker, Kubernetes API server, Consul,
Vault --- use \texttt{net/http} directly or with minimal routing
libraries. Understanding the standard library makes framework choices
deliberate rather than habitual.

\textbf{Production defaults without these timeouts:} a single slow

\texttt{ReadHeaderTimeout:\ 2s}, Slowloris attacks are mitigated. With
\texttt{WriteTimeout:\ 10s}, a slow consumer cannot hold a response
goroutine open indefinitely.

\hypertarget{key-takeaways}{%
\subsection{Key Takeaways}\label{key-takeaways}}

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  \textbf{\texttt{net/http} + Go 1.22 ServeMux} is sufficient for
  ARCHER's API --- no framework required.
\item
  \textbf{Timeouts on every dimension} of \texttt{http.Server} ---
  prevent resource exhaustion from slow clients.
\item
  \textbf{Middleware chain} applies cross-cutting concerns: request ID,
  logging, recovery, metrics.
\item
  \textbf{Handlers are thin closures} --- decode, validate, delegate,
  respond.
\item
  \textbf{Fresh context for async operations} started inside handlers
  --- never use \texttt{r.Context()} for background work.
\item
  \textbf{\texttt{/healthz} vs \texttt{/readyz}} --- liveness vs
  readiness; Kubernetes depends on both being correct.
\item
  \textbf{\texttt{r.Pattern} for Prometheus labels} --- prevents
  cardinality explosion from path parameters.
\end{enumerate}

\hypertarget{why-websockets-in-archer}{%
\subsection{1. Why WebSockets in
ARCHER}\label{why-websockets-in-archer}}

The ARCHER load test dashboard needs to display live metrics:
requests/second, P95 latency, error rate, active workers --- all
updating in real time as a load test runs. HTTP polling (client requests
every N seconds) wastes connections and introduces latency proportional
to the polling interval.

WebSockets solve this: a single persistent TCP connection, upgraded from
HTTP, through which the server pushes data to the client as it becomes
available. In ARCHER, the flow is:

\begin{verbatim}
Load Generator → MetricAccumulator → Telemetry Pipeline → WebSocket Hub → Dashboard Browser
\end{verbatim}

Every result from a worker is aggregated, and the current stats snapshot
is broadcast to all connected dashboard clients every second.

\textbf{The ping/pong mechanism:} WebSocket connections can silently die
(network partition, NAT timeout, phone going to sleep). The ticker sends
a \texttt{PingMessage} every 54 seconds. If no \texttt{PongMessage}
arrives within 60 seconds, \texttt{ReadMessage} times out and the read
pump exits, triggering cleanup. Without this, dead connections
accumulate indefinitely.

\hypertarget{scaling-websocket-connections}{%
\subsection{8. Scaling WebSocket
Connections}\label{scaling-websocket-connections}}

A single Go process with the Hub pattern handles tens of thousands of
concurrent WebSocket connections efficiently --- each client requires
\textasciitilde2 goroutines + the send channel buffer (256 ×
\textasciitilde32 bytes for JSON = \textasciitilde8KB). For 10,000
clients: 20,000 goroutines × 2KB = 40MB + 80MB for buffers =
\textasciitilde120MB. Reasonable.

\textbf{When you need to scale beyond one process:}

The Hub pattern breaks across multiple API server instances. A message
broadcast on instance A does not reach clients connected to instance B.
Solutions:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  \textbf{Redis Pub/Sub} --- publish broadcast messages to Redis; all
  instances subscribe
\item
  \textbf{Sticky sessions} --- route clients watching the same run to
  the same instance (Kubernetes sessionAffinity)
\item
  \textbf{Shared message broker} --- Kafka topic per run; all instances
  consume and broadcast locally
\end{enumerate}

For ARCHER's hackathon scope, sticky sessions are sufficient. For
production scale, Redis Pub/Sub:

\hypertarget{key-takeaways-1}{%
\subsection{Key Takeaways}\label{key-takeaways-1}}

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  \textbf{Hub pattern = single goroutine owns the subscriber map} --- no
  mutex required on the client set.
\item
  \textbf{Two goroutines per client}: read pump detects disconnection;
  write pump batches outbound messages.
\item
  \textbf{Ping/pong keepalive} is not optional --- silent disconnections
  accumulate without it.
\item
  \textbf{\texttt{CheckOrigin} is a security requirement} --- never use
  \texttt{func(r\ *http.Request)\ bool\ \{\ return\ true\ \}} in
  production.
\item
  \textbf{Client send buffer overflow = drop and disconnect} --- a slow
  consumer must not stall the hub.
\item
  \textbf{Broadcast to run-scoped client sets} --- enables multi-run
  dashboard with minimal overhead.
\item
  \textbf{Cross-instance broadcast requires Redis Pub/Sub or sticky
  sessions} --- the Hub pattern is per-process.
\end{enumerate}

\hypertarget{why-kafka-in-archer}{%
\subsection{1. Why Kafka in ARCHER}\label{why-kafka-in-archer}}

The ARCHER telemetry pipeline has a fundamental tension: the load
generator can produce 50,000--100,000 metric events per second, but the
database cannot absorb writes at that rate directly. Without a buffer,
the pipeline either drops events (lossy) or applies backpressure that
slows the load generator (inaccurate benchmarks).

Kafka solves this with \textbf{durable, ordered, replayable event
streams}:

\begin{verbatim}
Load Generator Workers
        │
        ▼  (high-speed writes)
  Kafka Topic: archer.metrics
        │
        ▼  (consumer-controlled pace)
  Telemetry Consumers
        │
        ▼  (batched writes)
  TimescaleDB / ClickHouse
\end{verbatim}

The load generator writes at full speed. Kafka buffers durably.
Consumers process at database-sustainable throughput. Events are never
lost --- they can be replayed from any offset if a consumer crashes.

\subsection{4. Manual vs Auto Commit --- Exactly-Once
Semantics}\label{manual-vs-auto-commit-exactly-once-semantics}}

\texttt{kafka-go} with \texttt{CommitInterval} auto-commits offsets
periodically. This provides \textbf{at-least-once} semantics: if the
consumer crashes between processing and committing, messages are
re-processed after restart.

For ARCHER metrics, at-least-once is acceptable --- duplicate metric
events result in slightly overcounted stats, not data corruption. For
financial transactions or billing events, you need exactly-once
semantics, which requires:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  \textbf{Manual offset commit} after successful processing
\item
  \textbf{Idempotent processing} (deduplicate on the consumer side)
\end{enumerate}

\hypertarget{topic-design-for-archer}{%
\subsection{7. Topic Design for ARCHER}\label{topic-design-for-archer}}

\begin{verbatim}
archer.metrics          — per-request telemetry from load generator workers
archer.runs             — run lifecycle events (created, started, completed, failed)
archer.alerts           — threshold breach notifications
archer.metrics.dlq      — dead-lettered unparseable metric events
\end{verbatim}

\textbf{Partition strategy:} - \texttt{archer.metrics}: partition by
\texttt{run\_id} (all events from a run in one partition, ordered) -
\texttt{archer.runs}: partition by \texttt{run\_id} (run state changes
are ordered per run) - \texttt{archer.alerts}: 1 partition (low volume,
global ordering acceptable)

\textbf{Retention policy:} - \texttt{archer.metrics}: 7 days or 100GB,
whichever first (replay window for debugging) - \texttt{archer.runs}: 30
days (audit log of all load test runs)

\hypertarget{consumer-group-scaling}{%
\subsection{9. Consumer Group Scaling}\label{consumer-group-scaling}}

Kafka consumer groups enable horizontal scaling of the telemetry
consumer:

\begin{verbatim}
archer.metrics topic (6 partitions)
    Partition 0, 1  → Consumer Instance A
    Partition 2, 3  → Consumer Instance B
    Partition 4, 5  → Consumer Instance C
\end{verbatim}

In Kubernetes, you run 3 replicas of the telemetry consumer service.
Kafka assigns 2 partitions per instance. If instance B crashes, Kafka
reassigns partitions 2 and 3 to A and C within \textasciitilde10 seconds
(session timeout).

\hypertarget{key-takeaways-2}{%
\subsection{Key Takeaways}\label{key-takeaways-2}}

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  \textbf{Kafka decouples producer throughput from consumer throughput}
  --- the load generator never slows down due to DB write speed.
\item
  \textbf{Partition by \texttt{run\_id}} --- ordering per run,
  parallelism across runs.
\item
  \textbf{Batch writes to Kafka and batch writes to DB} --- the two
  performance multipliers.
\item
  \textbf{At-least-once with DLQ} is the pragmatic pattern for
  telemetry; exactly-once for financial data.
\item
  \textbf{Consumer group replicas ≤ partition count} --- extra consumers
  idle above this ratio.
\item
  \textbf{Drop events at the emitter, not at the producer} --- preserve
  benchmark accuracy; accept telemetry loss under extreme pressure.
\item
  \textbf{\texttt{context.Canceled} from \texttt{ReadMessage} is a clean
  shutdown signal}, not an error.
\end{enumerate}

\hypertarget{graceful-shutdown-aligned-with-kubernetes}{%
\subsection{6. Graceful Shutdown Aligned with
Kubernetes}\label{graceful-shutdown-aligned-with-kubernetes}}

Kubernetes terminates pods in two phases:

\begin{verbatim}
Phase 1 (concurrent):
  - Pod removed from Service endpoints (new requests stop routing to this pod)
  - SIGTERM sent to PID 1 in the container

Phase 2 (after terminationGracePeriodSeconds = 30s by default):
  - SIGKILL sent to all processes — no more time

Gap between Phase 1 and your process receiving SIGTERM:
  - Kubernetes control plane propagates endpoint removal to kube-proxy/iptables
  - This takes 1-5 seconds in practice
\end{verbatim}

\textbf{The race condition}: if your service stops accepting new
connections immediately on SIGTERM, requests in-flight during that 1--5s
gap get connection refused. The fix: \textbf{add a pre-stop sleep}:

\begin{Shaded}
\begin{Highlighting}[]
\CommentTok{\# deploy/kubernetes/api{-}deployment.yaml}
\FunctionTok{spec}\KeywordTok{:}
\AttributeTok{  }\FunctionTok{containers}\KeywordTok{:}
\AttributeTok{  }\KeywordTok{{-}}\AttributeTok{ }\FunctionTok{name}\KeywordTok{:}\AttributeTok{ api}
\AttributeTok{    }\FunctionTok{lifecycle}\KeywordTok{:}
\AttributeTok{      }\FunctionTok{preStop}\KeywordTok{:}
\AttributeTok{        }\FunctionTok{exec}\KeywordTok{:}
\AttributeTok{          }\FunctionTok{command}\KeywordTok{:}\AttributeTok{ }\KeywordTok{[}\StringTok{"/bin/sleep"}\KeywordTok{,}\AttributeTok{ }\StringTok{"5"}\KeywordTok{]}\CommentTok{  \# wait for endpoint propagation}
\end{Highlighting}
\end{Shaded}

And your Go shutdown sequence:

\begin{Shaded}
\begin{Highlighting}[]
\KeywordTok{func}\NormalTok{ main}\OperatorTok{()} \OperatorTok{\{}
\NormalTok{    ctx}\OperatorTok{,}\NormalTok{ stop }\OperatorTok{:=}\NormalTok{ signal}\OperatorTok{.}\NormalTok{NotifyContext}\OperatorTok{(}\NormalTok{context}\OperatorTok{.}\NormalTok{Background}\OperatorTok{(),}\NormalTok{ os}\OperatorTok{.}\NormalTok{Interrupt}\OperatorTok{,}\NormalTok{ syscall}\OperatorTok{.}\NormalTok{SIGTERM}\OperatorTok{)}

\hypertarget{memory-limit-alignment}{%

Alignment}\label{memory-limit-alignment}}

Go's GC targets a heap size based on \texttt{GOGC} (default: 100 =
double heap before GC). If your container memory limit is 512MB and the
Go heap grows to 256MB, the GC triggers. If the heap grows to 512MB
before GC runs, the container is OOM-killed.

limit:

\hypertarget{key-takeaways-3}{%
\subsection{Key Takeaways}\label{key-takeaways-3}}

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  \textbf{\texttt{FROM\ scratch} + static binary} = minimal image,
  minimal attack surface, fast cold start.
\item
  \textbf{\texttt{automaxprocs}} aligns \texttt{GOMAXPROCS} with cgroup
  CPU quota --- mandatory in Kubernetes.
\item
  \textbf{\texttt{GOMEMLIMIT}} prevents OOM kills by triggering GC
  before reaching the container limit.
\item
  \textbf{preStop sleep + graceful shutdown} covers the Kubernetes
  endpoint propagation race.
\item
  \textbf{All config via environment variables} --- no hardcoded
  addresses; identical binary across environments.
\item
  \textbf{JSON to stdout} --- the only correct logging destination in
  containers.
\item
  \textbf{\texttt{/healthz} vs \texttt{/readyz}} --- liveness and
  readiness serve different Kubernetes functions.
\end{enumerate}
