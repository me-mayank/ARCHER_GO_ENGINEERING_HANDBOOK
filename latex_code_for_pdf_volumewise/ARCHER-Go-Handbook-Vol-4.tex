\hypertarget{preface-volume-4}{%
\subsection{Preface --- Volume 4}\label{preface-volume-4}}

A system that produces load but cannot tell you what happened is not an
observability platform --- it is a black box. Volume 4 turns the ARCHER
platform into a system that knows itself.

The telemetry pipeline chapter assembles the components from the
previous three volumes into a coherent dual-path ingestion system. A
single-goroutine event collector receives results from 50 concurrent
workers via a buffered channel --- no mutex, no contention. Every
second, it produces a snapshot and sends it simultaneously down two
independent paths: to the Kafka emitter for durable storage, and to the
WebSocket broadcaster for real-time dashboard delivery. A 30-second
sliding window produces the actionable percentiles displayed on the live
dashboard. Prometheus histograms (not summaries) instrument every stage.
The chapter explains why histograms are the only correct choice for
multi-instance percentile aggregation.

The logging and configuration chapter builds the operational foundation.
\texttt{zap} structured JSON logging with dynamic log level control via
\texttt{AtomicLevel} and an HTTP endpoint. A three-source configuration
system: compiled defaults overridden by YAML config files overridden by
environment variables --- the same priority order used by every
well-operated Kubernetes service. Validation that fails fast at startup,
before the first request is served. Configuration logged at startup
(excluding secrets) for incident triage.

The graceful shutdown chapter is the most operationally critical in the
curriculum. It defines the five-phase service lifecycle ---
initialization, readiness, serving, draining, termination --- and
provides the complete implementation for each. The shutdown timeout
budget calculation, reverse-dependency teardown ordering, goroutine leak
detection, and the preStop + terminationGracePeriodSeconds arithmetic
that eliminates connection refused errors during rolling Kubernetes
deployments.

The concurrency patterns chapter extends Volume 2's primitives to
production-scale throughput: \texttt{errgroup} for structured concurrent
fan-out, \texttt{singleflight} for collapsing duplicate concurrent
reads, \texttt{atomic.Pointer} for lock-free config hot-reload, cache
line padding for false sharing elimination, and pipeline backpressure
propagation as a correctness guarantee.

\hypertarget{what-a-telemetry-pipeline-is}{%
\subsection{1. What a Telemetry Pipeline
Is}\label{what-a-telemetry-pipeline-is}}

A telemetry pipeline is the data path from \textbf{event generation} to
\textbf{queryable observation}. In ARCHER, this spans:

\begin{verbatim}
Load Generator Workers
    │  (Result events — latency, status code, worker ID)
    ▼
MetricAccumulator  ← in-process, goroutine-safe
    │  (Snapshots every 1s)
    ▼
KafkaEmitter       ← batched, non-blocking
    │  (Topic: archer.metrics)
    ▼
Kafka Broker       ← durable buffer, 6 partitions
    │
    ▼
TelemetryConsumer  ← consumer group, 3 replicas
    │  (Batch writes every 500ms or 500 events)
    ▼
TimescaleDB        ← time-series storage
    │
    ▼
MetricBroadcaster  ← WebSocket hub
    │  (Snapshot every 1s per active run)
    ▼
Dashboard Browser
\end{verbatim}

Each stage has its own goroutine topology, its own failure mode, and its
own backpressure contract. This chapter assembles all prior concepts
into the complete pipeline.

\begin{center}\rule{0.5\linewidth}{0.5pt}\end{center}

\hypertarget{stage-1-in-process-metric-collection}{%
\subsection{2. Stage 1 --- In-Process Metric
Collection}\label{stage-1-in-process-metric-collection}}

The load generator's worker pool (Chapter 7) produces \texttt{Result}
events. These are collected by the \texttt{MetricAccumulator} (Chapter
3, Chapter 7). The accumulator must be:

\begin{itemize}
\tightlist
\item
  Goroutine-safe (concurrent workers write simultaneously)
\item
  Non-blocking on the write path (never slow a worker)
\item
  Snapshotting without blocking writes (readers don't pause writers)
\end{itemize}

\textbf{Why a single-goroutine collector?} This eliminates all locking
on the hot write path. The \texttt{CollectorState} is mutated only
inside \texttt{Run()}. Workers call \texttt{Collect()} which is a
buffered channel send --- a single CPU instruction at the hardware level
when the buffer isn't full.

\hypertarget{key-takeaways}{%
\subsection{Key Takeaways}\label{key-takeaways}}

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  \textbf{Single-goroutine collector = lock-free hot path.} Workers call
  a buffered channel send; state mutation is sequential.
\item
  \textbf{Dual-path publishing} --- Kafka for durability, WebSocket for
  real-time. They are independent failure domains.
\item
  \textbf{Snapshot is a value type} --- full copy ensures no data race
  between producer and consumer.
\item
  \textbf{Sliding window} for dashboard P95 --- more actionable than
  cumulative-since-run-start.
\item
  \textbf{Histograms not summaries} --- the only correct Prometheus
  instrument for multi-instance percentile aggregation.
\item
  \textbf{Pipeline self-observability} --- instrument every stage with
  counters, gauges, and histograms.
\item
  \textbf{Non-blocking emit path} --- telemetry loss is acceptable;
  benchmark accuracy is not.
\end{enumerate}

\hypertarget{environment-management-strategy}{%
\subsection{4. Environment Management
Strategy}\label{environment-management-strategy}}

\hypertarget{the-three-source-priority}{%
\subsubsection{4.1 The Three-Source
Priority}\label{the-three-source-priority}}

\begin{verbatim}
Priority (high → low):
1. Environment variables    ← Kubernetes Secrets / CI injection
2. Config file              ← Kubernetes ConfigMap / mounted file
3. Compiled defaults        ← safe fallback for non-critical settings
\end{verbatim}

Never hardcode environment-specific values in Go source code. If you
find yourself writing
\texttt{const\ kafkaBroker\ =\ "kafka.production.internal:9092"} in
application code, that's a config management failure.

\hypertarget{secrets-management}{%
\subsubsection{4.2 Secrets Management}\label{secrets-management}}

Secrets (database passwords, API keys, TLS certificates) must never
appear in: - Config YAML files committed to git - Docker images -
Environment variables visible in \texttt{docker\ inspect} output (for
truly sensitive values)

\hypertarget{the-service-lifecycle-model}{%
\subsection{1. The Service Lifecycle
Model}\label{the-service-lifecycle-model}}

A production Go service has five distinct lifecycle phases. Getting any
one wrong causes dropped requests, data loss, or zombie connections:

\begin{verbatim}
Phase 1: INITIALIZATION
  Load config → validate → create logger → connect dependencies

Phase 2: READINESS
  Run DB migrations → warm caches → verify Kafka connectivity
  /readyz returns 503 until all checks pass

Phase 3: SERVING
  Accept requests → process jobs → emit telemetry → broadcast results
  /readyz returns 200 → Kubernetes routes traffic here

Phase 4: DRAINING  ← triggered by SIGTERM
  Stop accepting new connections → complete in-flight requests
  Flush Kafka batches → commit consumer offsets → final telemetry snapshot

Phase 5: TERMINATION
  Close DB connections → close Kafka producer/consumer
  Flush logger → exit with code 0
\end{verbatim}

Most Go tutorials cover phases 1 and 3. ARCHER's reliability depends on
phases 2, 4, and 5 being implemented correctly.

\begin{center}\rule{0.5\linewidth}{0.5pt}\end{center}

\hypertarget{zero-downtime-deployments}{%
\subsection{9. Zero-Downtime
Deployments}\label{zero-downtime-deployments}}

In Kubernetes, a rolling deployment replaces pods one at a time. Without
correct lifecycle management, users see brief errors during each pod
replacement. The requirements for zero-downtime:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  \textbf{New pods become ready} before old pods receive SIGTERM

  \begin{itemize}
  \tightlist
  \item
    Readiness probe passes on new pod → Kubernetes adds to endpoints
  \item
    SIGTERM sent to old pod → old pod starts draining
  \end{itemize}
\item
  \textbf{Old pods drain cleanly} before SIGKILL

  \begin{itemize}
  \tightlist
  \item
    \texttt{preStop} sleep covers endpoint propagation lag
  \item
    \texttt{server.Shutdown} drains in-flight requests
  \end{itemize}
\item
  \textbf{Shared state survives pod restart}

  \begin{itemize}
  \tightlist
  \item
    Kafka offsets committed --- consumer restarts from last committed
    offset
  \item
    No in-memory state that's lost on restart (all state in DB / Kafka)
  \item
    WebSocket clients reconnect --- the dashboard reconnects on
    disconnect
  \end{itemize}
\end{enumerate}

\begin{Shaded}
\begin{Highlighting}[]

\CommentTok{// Your Go backend doesn\textquotesingle{}t implement this, but it must support it:}
\CommentTok{// {-} WebSocket close code 1001 (Going Away) signals graceful shutdown}
\CommentTok{// {-} Client retries with exponential backoff}
\CommentTok{// {-} New connection is served by another pod immediately}

\hypertarget{beyond-basic-concurrency}{%
\subsection{1. Beyond Basic
Concurrency}\label{beyond-basic-concurrency}}

Chapters 5 and 6 established goroutines, the GMP scheduler, and
foundational channel patterns. Chapter 7 built the worker pool. This
chapter goes further: the patterns that separate a system handling 10k
req/s from one handling 500k req/s --- not by adding hardware, but by
eliminating contention, reducing allocations, and restructuring data
flow.

The performance ceiling in concurrent Go systems is almost never raw CPU
throughput. It is: 1. \textbf{Lock contention} --- goroutines waiting
for mutexes 2. \textbf{Allocation pressure} --- GC pauses from
per-request heap allocations 3. \textbf{Channel overhead} ---
unnecessary goroutine wakeups 4. \textbf{Cache line contention} ---
false sharing between atomics on adjacent memory

Each section below addresses one of these ceilings.

\hypertarget{the-errgroup-pattern-structured-concurrency}{%

\texttt{errgroup} (Chapter 4) is Go's answer to structured concurrency:

For ARCHER's multi-target load testing (benchmarking multiple endpoints
simultaneously):

\subsection{8. The Pipeline with Backpressure

A pipeline without backpressure is a pipeline that crashes under load.
The ARCHER telemetry pipeline propagates backpressure upstream:

\hypertarget{key-takeaways-3}{%
\subsection{Key Takeaways}\label{key-takeaways-3}}

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  \textbf{\texttt{errgroup} for structured concurrency} --- shared
  lifetime, first error cancels all.
\item
  \textbf{\texttt{singleflight} collapses duplicate concurrent requests}
  --- critical for read-heavy APIs.
\item
  \textbf{\texttt{atomic.Pointer}} for lock-free config hot-reload
  without stopping workers.
\item
  \textbf{False sharing} between adjacent atomics --- pad to 64-byte
  cache lines in profiled hot paths.
\item
  \textbf{Pipeline backpressure} flows from slowest stage upstream ---
  buffer sizes are contracts, not suggestions.
\item
  \textbf{Profile before optimizing} --- mutex contention, heap
  allocations, and goroutine stalls are visible.
\item
  \textbf{Array sharding} (distinct index per goroutine) eliminates
  synchronization on slice writes.
\end{enumerate}
