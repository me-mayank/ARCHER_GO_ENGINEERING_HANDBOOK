\hypertarget{preface-volume-1}{%
\subsection{Preface --- Volume 1}\label{preface-volume-1}}

Go was designed for infrastructure. Not web forms, not enterprise CRUD,
not desktop applications --- infrastructure. Networked services,
concurrent backends, containerized workers, distributed coordination
systems. The language's design choices --- goroutines over threads,
channels over shared memory, static binaries over managed runtimes,
explicit error returns over exceptions --- are not arbitrary
preferences. They are engineering decisions optimized for the specific
failure modes of distributed systems at scale.

This volume lays the mental foundation without which every subsequent
chapter is syntax without insight. It begins with the Go mental model:
how Go thinks about concurrency, ownership, memory, and deployment, and
why those choices make it uniquely suited for the backends that power
modern infrastructure. It then addresses project structure --- the
canonical \texttt{cmd/internal/pkg} layout that governs every Go
backend, the discipline of manual dependency injection, and the
configuration architecture that makes services portable across
environments.

The third chapter addresses types: how Go's structural typing,
embedding, and interface design enable composable systems without the
inheritance hierarchies of Java or the template complexity of C++. The
fourth chapter addresses a question every engineer from an
exception-based language must answer definitively: what is the correct
philosophy for handling failure in a distributed system where partial
success is the norm, not the exception?

By the end of Volume 1, you will think in Go --- not just write it.

\hypertarget{preface-why-this-chapter-exists}{%
\subsection{Preface: Why This Chapter
Exists}\label{preface-why-this-chapter-exists}}

Before you write a single line of Go for a load generator, telemetry
pipeline, or WebSocket service, you need to rewire the mental model
you've built in C++ or Java. This is not about syntax. It is about how
Go forces you to think about \textbf{ownership, concurrency, deployment,
and composition} differently --- and why those constraints make it
exceptional for distributed backend systems.

This chapter is intentionally philosophical and architectural. Code
appears here only to ground ideas in reality.

\begin{center}\rule{0.5\linewidth}{0.5pt}\end{center}

\hypertarget{gos-design-intent-built-for-the-infrastructure-layer}{%
\subsection{1. Go's Design Intent --- Built for the Infrastructure
Layer}\label{gos-design-intent-built-for-the-infrastructure-layer}}

Go was created at Google in 2007 to solve a specific class of problems:
\textbf{large-scale networked server infrastructure} written by many
engineers simultaneously, deployed in containers, and expected to handle
millions of concurrent connections with predictable latency.

The language was designed by: - \textbf{Rob Pike} --- systems
programming, concurrency models - \textbf{Ken Thompson} --- Unix, C,
compilers - \textbf{Robert Griesemer} --- V8, HotSpot JVM internals

The design constraints were not academic. They were operational:

\begin{longtable}[]{@{}
  >{\raggedright\arraybackslash}p{(\columnwidth - 2\tabcolsep) * \real{0.5000}}
  >{\raggedright\arraybackslash}p{(\columnwidth - 2\tabcolsep) * \real{0.5000}}@{}}
\toprule()
\begin{minipage}[b]{\linewidth}\raggedright
Constraint
\end{minipage} & \begin{minipage}[b]{\linewidth}\raggedright
Implication
\end{minipage} \\
\midrule()
\endhead
Fast compile times & Engineers never wait; CI is fast \\
Single static binary output & Docker images are trivial; no JVM, no
runtime deps \\
GC with sub-millisecond pauses & Predictable latency in tight feedback
loops \\
CSP-based concurrency & Concurrent I/O without callback pyramids or
thread pools \\
Explicit error values & No hidden exceptions propagating up call
stacks \\
Structural typing & Composition without inheritance hierarchies \\
\bottomrule()
\end{longtable}

This is not a language designed for ML pipelines or front-end rendering.
It is designed for \textbf{the infrastructure tier}: HTTP servers, RPC
services, event consumers, orchestrators, telemetry collectors.

If you come from C++, think of Go as: ``What if we kept the performance
culture, removed UB and memory management complexity, and built
first-class networked I/O into the runtime?''

If you come from Java, think of Go as: ``What if we removed the class
hierarchy religion, eliminated checked exceptions, made binaries
self-contained, and let concurrency feel natural?''

\begin{center}\rule{0.5\linewidth}{0.5pt}\end{center}

\hypertarget{the-compiled-binary-mental-model}{%
\subsection{2. The Compiled Binary Mental
Model}\label{the-compiled-binary-mental-model}}

In C++, you build a binary that links against system libs, shared
\texttt{.so} files, and occasionally a runtime. Deployment is artifact
management.

In Java, you ship a \texttt{.jar}, the JVM is pre-installed, and your
classpath must be configured.

In Go:

\begin{lstlisting}[language=Go]
\VariableTok{GOOS}\OperatorTok{=}\NormalTok{linux }\VariableTok{GOARCH}\OperatorTok{=}\NormalTok{amd64 }\ExtensionTok{go}\NormalTok{ build }\AttributeTok{{-}o}\NormalTok{ archer{-}agent ./cmd/agent/}
\end{lstlisting}

That command produces a \textbf{single, statically-linked ELF binary}
with zero external runtime dependencies. The entire program --- your
code, the standard library, the goroutine scheduler, the GC --- is
inside that binary.

\begin{lstlisting}[language=Go]
\KeywordTok{FROM}\NormalTok{ scratch}
\KeywordTok{COPY}\NormalTok{ archer{-}agent /archer{-}agent}
\KeywordTok{ENTRYPOINT}\NormalTok{ [}\StringTok{"/archer{-}agent"}\NormalTok{]}
\end{lstlisting}

This is a legitimate, production-grade Dockerfile. The image is 12--20
MB. There is no base OS layer. There is no JVM or interpreter. The
container boots in milliseconds.

\textbf{Why this matters for distributed systems:} - Your Kubernetes
pods are cheap to schedule - Cold-start latency is deterministic - You
can run 100 replicas of a telemetry agent without worrying about
per-process JVM overhead - Security surface is minimal --- no shell, no
package manager, no libc (optionally)

This ``binary as the unit of deployment'' mental model fundamentally
changes how you architect services. Each Go service should be a
\textbf{standalone capability} that starts, connects, and operates
independently.

\begin{center}\rule{0.5\linewidth}{0.5pt}\end{center}

\hypertarget{the-goroutine-mental-model-not-threads}{%
\subsection{3. The Goroutine Mental Model --- Not
Threads}\label{the-goroutine-mental-model-not-threads}}

This is the single most important cognitive shift.

\hypertarget{c-thread-model}{%
\subsubsection{3.1 C++ Thread Model}\label{c-thread-model}}

In C++, concurrency means OS threads. Each thread: - Costs
\textasciitilde1--8 MB of stack by default - Is scheduled by the OS
kernel - Context switching involves system calls (expensive) - Shared
state requires mutexes, semaphores, atomic ops - A server handling
10,000 concurrent connections needs 10,000 threads → resource exhaustion

The ``solution'' in C++ is async I/O: \texttt{epoll},
\texttt{io\_uring}, \texttt{libuv}, \texttt{Boost.Asio}. You write
callback chains, state machines, or coroutines to avoid
thread-per-connection. It works, but the code is structurally complex.

\hypertarget{java-thread-model}{%
\subsubsection{3.2 Java Thread Model}\label{java-thread-model}}

Java historically used OS threads. The M:N virtual thread model (Project
Loom) arrived late. The ecosystem defaulted to thread pools
(ExecutorService), reactive streams (Project Reactor, RxJava), and async
frameworks (Spring WebFlux). Each comes with significant cognitive
overhead: callback composition, scheduler configuration, blocking
detection.

\hypertarget{go-goroutine-model}{%
\subsubsection{3.3 Go Goroutine Model}\label{go-goroutine-model}}

A goroutine is a \textbf{Green Thread} managed entirely by the Go
runtime. Key properties:

\begin{longtable}[]{@{}ll@{}}
\toprule()
Property & Value \\
\midrule()
\endhead
Initial stack size & \textasciitilde2 KB (grows dynamically) \\
Max goroutines on modern hardware & Hundreds of thousands \\
Scheduling model & M:N (many goroutines on N OS threads) \\
Context switch cost & \textasciitilde200ns (vs \textasciitilde1µs for OS
thread) \\
I/O blocking behavior & Goroutine parks; OS thread is reused \\
\bottomrule()
\end{longtable}

When a goroutine blocks on I/O (network read, file write, syscall), the
Go runtime \textbf{parks that goroutine} and puts another runnable
goroutine on the same OS thread. You write code that looks synchronous
but executes asynchronously at the runtime level.

\begin{lstlisting}[language=Go]
\CommentTok{// This looks like a blocking call — it is NOT blocking an OS thread}
\KeywordTok{func}\NormalTok{ handleConnection}\OperatorTok{(}\NormalTok{conn net}\OperatorTok{.}\NormalTok{Conn}\OperatorTok{)} \OperatorTok{\{}
\NormalTok{    buf }\OperatorTok{:=} \BuiltInTok{make}\OperatorTok{([]}\DataTypeTok{byte}\OperatorTok{,} \DecValTok{4096}\OperatorTok{)}
\NormalTok{    n}\OperatorTok{,}\NormalTok{ err }\OperatorTok{:=}\NormalTok{ conn}\OperatorTok{.}\NormalTok{Read}\OperatorTok{(}\NormalTok{buf}\OperatorTok{)} \CommentTok{// goroutine parks here; OS thread serves other goroutines}
    \ControlFlowTok{if}\NormalTok{ err }\OperatorTok{!=} \OtherTok{nil} \OperatorTok{\{}
        \ControlFlowTok{return}
    \OperatorTok{\}}
\NormalTok{    process}\OperatorTok{(}\NormalTok{buf}\OperatorTok{[:}\NormalTok{n}\OperatorTok{])}
\OperatorTok{\}}

\KeywordTok{func}\NormalTok{ main}\OperatorTok{()} \OperatorTok{\{}
\NormalTok{    ln}\OperatorTok{,}\NormalTok{ \_ }\OperatorTok{:=}\NormalTok{ net}\OperatorTok{.}\NormalTok{Listen}\OperatorTok{(}\StringTok{"tcp"}\OperatorTok{,} \StringTok{":8080"}\OperatorTok{)}
    \ControlFlowTok{for} \OperatorTok{\{}
\NormalTok{        conn}\OperatorTok{,}\NormalTok{ \_ }\OperatorTok{:=}\NormalTok{ ln}\OperatorTok{.}\NormalTok{Accept}\OperatorTok{()}
        \ControlFlowTok{go}\NormalTok{ handleConnection}\OperatorTok{(}\NormalTok{conn}\OperatorTok{)} \CommentTok{// spawn goroutine — 2KB stack, \textasciitilde{}100ns cost}
    \OperatorTok{\}}
\OperatorTok{\}}
\end{lstlisting}

This loop handles tens of thousands of concurrent connections without a
thread pool configuration. The runtime schedules goroutines across
\texttt{GOMAXPROCS} OS threads (default: number of CPU cores).

\textbf{The mental model shift}: Stop thinking in ``thread pools'' and
``thread counts.'' Think in ``goroutines per request'' or ``goroutines
per connection.'' They are cheap enough to create per-operation.

\begin{center}\rule{0.5\linewidth}{0.5pt}\end{center}

\hypertarget{the-communication-mental-model-csp-over-shared-memory}{%
\subsection{4. The Communication Mental Model --- CSP over Shared
Memory}\label{the-communication-mental-model-csp-over-shared-memory}}

Go's concurrency philosophy is:

\begin{quote}
``Do not communicate by sharing memory; instead, share memory by
communicating.'' --- Rob Pike
\end{quote}

This is Communicating Sequential Processes (CSP), formalized by Tony
Hoare in 1978. Go implements it via \textbf{channels}.

\hypertarget{why-shared-memory-is-dangerous-at-scale}{%
\subsubsection{4.1 Why Shared Memory Is Dangerous at
Scale}\label{why-shared-memory-is-dangerous-at-scale}}

In a load generator, you might have 500 concurrent goroutines sending
HTTP requests and aggregating latency metrics into a shared struct. With
shared memory:

\begin{lstlisting}[language=Go]
\CommentTok{// }\AlertTok{DANGER}\CommentTok{: data race — multiple goroutines writing concurrently}
\KeywordTok{type}\NormalTok{ Metrics }\KeywordTok{struct} \OperatorTok{\{}
\NormalTok{    TotalRequests }\DataTypeTok{int64}
\NormalTok{    TotalLatency  }\DataTypeTok{int64}
\OperatorTok{\}}

\KeywordTok{var}\NormalTok{ globalMetrics Metrics}

\KeywordTok{func}\NormalTok{ sendRequest}\OperatorTok{(}\NormalTok{m }\OperatorTok{*}\NormalTok{Metrics}\OperatorTok{)} \OperatorTok{\{}
\NormalTok{    start }\OperatorTok{:=}\NormalTok{ time}\OperatorTok{.}\NormalTok{Now}\OperatorTok{()}
    \CommentTok{// ... send request ...}
\NormalTok{    m}\OperatorTok{.}\NormalTok{TotalRequests}\OperatorTok{++}                              \CommentTok{// data race}
\NormalTok{    m}\OperatorTok{.}\NormalTok{TotalLatency }\OperatorTok{+=}\NormalTok{ time}\OperatorTok{.}\NormalTok{Since}\OperatorTok{(}\NormalTok{start}\OperatorTok{).}\NormalTok{Nanoseconds}\OperatorTok{()} \CommentTok{// data race}
\OperatorTok{\}}
\end{lstlisting}

Go's race detector (\texttt{go\ run\ -race}) will flag this. The fix
requires mutexes or atomics, which introduces contention and locking
discipline.

\hypertarget{the-error-handling-mental-model}{%
\subsection{5. The Error Handling Mental
Model}\label{the-error-handling-mental-model}}

Go has no exceptions. Errors are values returned from functions.

\begin{lstlisting}[language=Go]
\NormalTok{result}\OperatorTok{,}\NormalTok{ err }\OperatorTok{:=}\NormalTok{ doSomething}\OperatorTok{()}
\ControlFlowTok{if}\NormalTok{ err }\OperatorTok{!=} \OtherTok{nil} \OperatorTok{\{}
    \ControlFlowTok{return}\NormalTok{ fmt}\OperatorTok{.}\NormalTok{Errorf}\OperatorTok{(}\StringTok{"context about what failed: \%w"}\OperatorTok{,}\NormalTok{ err}\OperatorTok{)}
\OperatorTok{\}}
\end{lstlisting}

Coming from C++ (exceptions, error codes) or Java (checked/unchecked
exceptions), this feels verbose. It is. It is also \textbf{explicit
about every failure path}, which is what you want in production systems.

\hypertarget{why-exceptions-are-dangerous-in-distributed-systems}{%
\subsubsection{5.1 Why Exceptions Are Dangerous in Distributed
Systems}\label{why-exceptions-are-dangerous-in-distributed-systems}}

In a Kafka consumer loop that processes telemetry events, an unhandled
exception in Java causes the goroutine (or thread) to crash silently, or
requires a top-level catch-all that swallows context. In Go, every error
is visible in the call chain. You decide: retry, log-and-skip, or
escalate.

\begin{lstlisting}[language=Go]
\KeywordTok{func}\NormalTok{ processKafkaMessage}\OperatorTok{(}\NormalTok{msg kafka}\OperatorTok{.}\NormalTok{Message}\OperatorTok{)} \DataTypeTok{error} \OperatorTok{\{}
\NormalTok{    event}\OperatorTok{,}\NormalTok{ err }\OperatorTok{:=}\NormalTok{ parseEvent}\OperatorTok{(}\NormalTok{msg}\OperatorTok{.}\NormalTok{Value}\OperatorTok{)}
    \ControlFlowTok{if}\NormalTok{ err }\OperatorTok{!=} \OtherTok{nil} \OperatorTok{\{}
        \ControlFlowTok{return}\NormalTok{ fmt}\OperatorTok{.}\NormalTok{Errorf}\OperatorTok{(}\StringTok{"parse failed for offset \%d: \%w"}\OperatorTok{,}\NormalTok{ msg}\OperatorTok{.}\NormalTok{Offset}\OperatorTok{,}\NormalTok{ err}\OperatorTok{)}
    \OperatorTok{\}}

    \ControlFlowTok{if}\NormalTok{ err }\OperatorTok{:=}\NormalTok{ storeMetric}\OperatorTok{(}\NormalTok{event}\OperatorTok{);}\NormalTok{ err }\OperatorTok{!=} \OtherTok{nil} \OperatorTok{\{}
        \ControlFlowTok{return}\NormalTok{ fmt}\OperatorTok{.}\NormalTok{Errorf}\OperatorTok{(}\StringTok{"store failed for event \%s: \%w"}\OperatorTok{,}\NormalTok{ event}\OperatorTok{.}\NormalTok{ID}\OperatorTok{,}\NormalTok{ err}\OperatorTok{)}
    \OperatorTok{\}}

    \ControlFlowTok{return} \OtherTok{nil}
\OperatorTok{\}}

\KeywordTok{func}\NormalTok{ consumerLoop}\OperatorTok{(}\NormalTok{consumer kafka}\OperatorTok{.}\NormalTok{Consumer}\OperatorTok{)} \OperatorTok{\{}
    \ControlFlowTok{for} \OperatorTok{\{}
\NormalTok{        msg}\OperatorTok{,}\NormalTok{ err }\OperatorTok{:=}\NormalTok{ consumer}\OperatorTok{.}\NormalTok{ReadMessage}\OperatorTok{({-}}\DecValTok{1}\OperatorTok{)}
        \ControlFlowTok{if}\NormalTok{ err }\OperatorTok{!=} \OtherTok{nil} \OperatorTok{\{}
\NormalTok{            log}\OperatorTok{.}\NormalTok{Printf}\OperatorTok{(}\StringTok{"kafka read error: \%v"}\OperatorTok{,}\NormalTok{ err}\OperatorTok{)}
            \ControlFlowTok{continue} \CommentTok{// decide: retry or exit}
        \OperatorTok{\}}

        \ControlFlowTok{if}\NormalTok{ err }\OperatorTok{:=}\NormalTok{ processKafkaMessage}\OperatorTok{(}\NormalTok{msg}\OperatorTok{);}\NormalTok{ err }\OperatorTok{!=} \OtherTok{nil} \OperatorTok{\{}
\NormalTok{            log}\OperatorTok{.}\NormalTok{Printf}\OperatorTok{(}\StringTok{"processing failed: \%v"}\OperatorTok{,}\NormalTok{ err}\OperatorTok{)} \CommentTok{// error is wrapped with full context}
            \CommentTok{// decide: dead{-}letter queue, skip, or halt}
        \OperatorTok{\}}
    \OperatorTok{\}}
\OperatorTok{\}}
\end{lstlisting}

The \texttt{\%w} verb wraps errors so callers can use
\texttt{errors.Is()} and \texttt{errors.As()} to inspect the error
chain. The full context is preserved: ``store failed for event abc123:
connection refused: dial tcp 10.0.0.5:5432''.

\hypertarget{the-interface-mental-model-structural-typing-vs-nominal-typing}{%
\subsection{6. The Interface Mental Model --- Structural Typing vs
Nominal
Typing}\label{the-interface-mental-model-structural-typing-vs-nominal-typing}}

In Java and C++, a type must explicitly declare that it implements an
interface:

\begin{lstlisting}[language=Go]
\CommentTok{// Java — explicit declaration}
\KeywordTok{class}\NormalTok{ KafkaMetricStore }\KeywordTok{implements}\NormalTok{ MetricStore }\OperatorTok{\{} \KeywordTok{...} \OperatorTok{\}}
\end{lstlisting}

In Go, \textbf{if a type has the required methods, it satisfies the
interface}. No explicit declaration. This is structural (duck) typing.

\begin{lstlisting}[language=Go]
\KeywordTok{type}\NormalTok{ MetricStore }\KeywordTok{interface} \OperatorTok{\{}
\NormalTok{    Store}\OperatorTok{(}\NormalTok{m Metric}\OperatorTok{)} \DataTypeTok{error}
\NormalTok{    Query}\OperatorTok{(}\NormalTok{id }\DataTypeTok{string}\OperatorTok{)} \OperatorTok{(}\NormalTok{Metric}\OperatorTok{,} \DataTypeTok{error}\OperatorTok{)}
\OperatorTok{\}}

\CommentTok{// PostgresStore satisfies MetricStore without any declaration}
\KeywordTok{type}\NormalTok{ PostgresStore }\KeywordTok{struct} \OperatorTok{\{}\NormalTok{ db }\OperatorTok{*}\NormalTok{sql}\OperatorTok{.}\NormalTok{DB }\OperatorTok{\}}
\KeywordTok{func} \OperatorTok{(}\NormalTok{s }\OperatorTok{*}\NormalTok{PostgresStore}\OperatorTok{)}\NormalTok{ Store}\OperatorTok{(}\NormalTok{m Metric}\OperatorTok{)} \DataTypeTok{error}  \OperatorTok{\{} \OperatorTok{...} \OperatorTok{\}}
\KeywordTok{func} \OperatorTok{(}\NormalTok{s }\OperatorTok{*}\NormalTok{PostgresStore}\OperatorTok{)}\NormalTok{ Query}\OperatorTok{(}\NormalTok{id }\DataTypeTok{string}\OperatorTok{)} \OperatorTok{(}\NormalTok{Metric}\OperatorTok{,} \DataTypeTok{error}\OperatorTok{)} \OperatorTok{\{} \OperatorTok{...} \OperatorTok{\}}

\CommentTok{// RedisCache also satisfies MetricStore}
\KeywordTok{type}\NormalTok{ RedisCache }\KeywordTok{struct} \OperatorTok{\{}\NormalTok{ client }\OperatorTok{*}\NormalTok{redis}\OperatorTok{.}\NormalTok{Client }\OperatorTok{\}}
\KeywordTok{func} \OperatorTok{(}\NormalTok{r }\OperatorTok{*}\NormalTok{RedisCache}\OperatorTok{)}\NormalTok{ Store}\OperatorTok{(}\NormalTok{m Metric}\OperatorTok{)} \DataTypeTok{error}  \OperatorTok{\{} \OperatorTok{...} \OperatorTok{\}}
\KeywordTok{func} \OperatorTok{(}\NormalTok{r }\OperatorTok{*}\NormalTok{RedisCache}\OperatorTok{)}\NormalTok{ Query}\OperatorTok{(}\NormalTok{id }\DataTypeTok{string}\OperatorTok{)} \OperatorTok{(}\NormalTok{Metric}\OperatorTok{,} \DataTypeTok{error}\OperatorTok{)} \OperatorTok{\{} \OperatorTok{...} \OperatorTok{\}}
\end{lstlisting}

\textbf{Why this matters architecturally:} - You can define small,
focused interfaces at the \emph{consumption site}, not the definition
site - Mock implementations for testing are trivial - You can swap
\texttt{PostgresStore} for \texttt{RedisCache} in a worker pool with
zero changes to the worker - Interfaces stay narrow because you only
define what you use

This enables the \textbf{composition-over-inheritance} architecture that
makes Go backends testable and modular.

Go binaries are 5--30 MB depending on dependency tree. They start in

\hypertarget{the-gc-tradeoff}{%
\subsubsection{8.2 The GC Tradeoff}\label{the-gc-tradeoff}}

Go's GC is a concurrent, tri-color mark-and-sweep. It runs concurrently
with your program. Pause times are typically sub-millisecond for most
workloads. You sacrifice some throughput for predictable latency.

In a telemetry pipeline ingesting 100k events/second, a 50ms GC pause in
Java can cause buffer overflow and data loss. Go's sub-millisecond
pauses keep the pipeline steady.

You manage GC pressure by: - Reusing objects via \texttt{sync.Pool} -
Avoiding unnecessary allocations in hot paths - Using value semantics
(stack allocation) vs pointer semantics (heap allocation)

\begin{enumerate}

\end{itemize}

\hypertarget{preface-why-structure-is-an-architectural-decision}{%
\subsection{Preface: Why Structure Is an Architectural
Decision}\label{preface-why-structure-is-an-architectural-decision}}

In C++, project structure is determined by build systems (CMake, Bazel,
Make). In Java, it follows Maven/Gradle conventions enforced by
frameworks (Spring Boot, Quarkus). In Go, the language itself provides
minimal opinion --- and the community has evolved strong conventions
that reflect the distribution and deployment model of Go services.

Getting structure wrong costs you in team velocity, refactoring pain,
circular import errors, and binary bloat. Getting it right means your
engineers can navigate a 200-file backend codebase confidently on day
one.

This chapter covers the canonical Go project layout for distributed
backend systems and explains \textbf{why} each structural decision
exists.

\begin{center}\rule{0.5\linewidth}{0.5pt}\end{center}

\hypertarget{the-go-module-system-first-principles}{%
\subsection{1. The Go Module System --- First
Principles}\label{the-go-module-system-first-principles}}

\hypertarget{modules-vs-packages}{%
\subsubsection{1.1 Modules vs Packages}\label{modules-vs-packages}}

A \textbf{module} is the top-level dependency and versioning unit.
Declared by \texttt{go.mod}. One module per repository in most
production systems.

A \textbf{package} is the compilation and import unit. Every
\texttt{.go} file belongs to exactly one package. Package name ==
directory name (by convention).

\begin{verbatim}
module github.com/org/archer

go 1.22

require (
    github.com/gorilla/websocket v1.5.0
    github.com/segmentio/kafka-go v0.4.47
    go.uber.org/zap v1.26.0
)
\end{verbatim}

The module path (\texttt{github.com/org/archer}) is the import prefix
for all internal packages:

\begin{lstlisting}[language=Go]
\KeywordTok{import} \OperatorTok{(}
    \StringTok{"github.com/org/archer/internal/telemetry"}
    \StringTok{"github.com/org/archer/pkg/loadgen"}
\OperatorTok{)}
\end{lstlisting}

\textbf{Key insight}: The module path is the global namespace for your
entire codebase. Choose it once; it appears in every import.

\hypertarget{go.sum-and-reproducible-builds}{%
\subsubsection{\texorpdfstring{1.2 \texttt{go.sum} and Reproducible
Builds}{1.2 go.sum and Reproducible Builds}}\label{go.sum-and-reproducible-builds}}

\texttt{go.sum} contains cryptographic hashes of every dependency.
Committed to version control. Docker builds are reproducible because
\texttt{go\ mod\ download} will verify hashes match.

\begin{lstlisting}[language=Go]
\KeywordTok{COPY}\NormalTok{ go.mod go.sum ./}
\KeywordTok{RUN} \ExtensionTok{go}\NormalTok{ mod download  }\CommentTok{\# cached layer; only invalidated when deps change}
\KeywordTok{COPY}\NormalTok{ . .}
\KeywordTok{RUN} \ExtensionTok{go}\NormalTok{ build ./cmd/...}
\end{lstlisting}

This Docker layer caching strategy means your builds are fast even in CI
because the \texttt{go\ mod\ download} layer is cached as long as
\texttt{go.mod}/\texttt{go.sum} are unchanged.

\hypertarget{the-internal-enforcement-rule}{%
\subsubsection{\texorpdfstring{4.1 The \texttt{internal} Enforcement
Rule}{4.1 The internal Enforcement Rule}}\label{the-internal-enforcement-rule}}

Go enforces that packages under \texttt{internal/} \textbf{cannot be
imported by code outside the module}. This is a compiler-enforced API
boundary.

\begin{verbatim}
archer/internal/kafka/ → importable only by code in archer/
external-module/       → cannot import archer/internal/kafka/
\end{verbatim}

This matters enormously in distributed systems where you may publish
shared libraries. \texttt{internal/} guarantees that your implementation
packages are \textbf{never accidentally used as public API}.

\hypertarget{package-design-principles-for-distributed-systems}{%
\subsection{6. Package Design Principles for Distributed
Systems}\label{package-design-principles-for-distributed-systems}}

\hypertarget{package-cohesion-single-responsibility}{%
\subsubsection{6.1 Package Cohesion --- Single
Responsibility}\label{package-cohesion-single-responsibility}}

A package should represent a \textbf{single capability} or
\textbf{single domain concept}. Not a file of utilities.

\begin{verbatim}
BAD:
internal/utils/         # Dumping ground for everything
    string_helpers.go
    http_helpers.go
    kafka_helpers.go
    db_helpers.go

GOOD:
internal/httputil/      # HTTP-specific utilities
internal/kafkautil/     # Kafka-specific wrappers
internal/store/         # Database access layer
\end{verbatim}

When \texttt{utils/} exists, it means the team hasn't thought through
ownership. In a distributed system with multiple engineers, unclear
ownership is a maintenance tax.

\hypertarget{avoid-circular-imports-design-with-dependency-direction}{%
\subsubsection{6.2 Avoid Circular Imports --- Design with Dependency
Direction}\label{avoid-circular-imports-design-with-dependency-direction}}

Go prohibits circular imports at compile time. This is a feature. It
forces a layered dependency graph:

\begin{verbatim}
cmd/ → internal/ → pkg/ → stdlib
cmd/ → internal/ → (never back to cmd/)
internal/kafka/ → (never imports internal/telemetry/ if telemetry imports kafka/)
\end{verbatim}

If you find yourself needing a circular import, you have a design
problem. The solutions are: 1. Extract the shared type into a third
package both can import 2. Use an interface to invert the dependency 3.
Merge the packages if they're truly inseparable

\begin{lstlisting}[language=Go]

\CommentTok{// Solution: extract shared type to pkg/protocol/}

\KeywordTok{type}\NormalTok{ TelemetryEvent }\KeywordTok{struct} \OperatorTok{\{}
    \CommentTok{// shared type that both kafka and telemetry packages import}
\OperatorTok{\}}
\end{lstlisting}

\hypertarget{package-naming-no-generic-names}{%
\subsubsection{6.3 Package Naming --- No Generic
Names}\label{package-naming-no-generic-names}}

\begin{verbatim}
BAD:  package common, package util, package base, package shared
GOOD: package telemetry, package loadgen, package worker, package kafkaclient
\end{verbatim}

Package names appear at every import site.
\texttt{telemetry.NewPipeline()} is self-documenting.
\texttt{common.NewPipeline()} is not.

\hypertarget{production-checklist-1}{%
\subsection{Production Checklist}\label{production-checklist-1}}

\begin{itemize}
\tightlist
\item[$\square$]
  Each binary has its own \texttt{cmd/*/main.go} with only wiring logic
\item[$\square$]
  All business logic lives in \texttt{internal/} packages
\item[$\square$]
  Interfaces defined in consumer packages, not provider packages
\item[$\square$]
  \texttt{MemoryXxx} test implementations for all store interfaces
\item[$\square$]
  Config loaded and validated at startup via typed struct
\item[$\square$]
  Multi-stage Dockerfile with \texttt{FROM\ scratch} final stage
\item[$\square$]
  \texttt{go\ mod\ tidy} run before every commit
\item[$\square$]
  \texttt{-race} flag in all test runs
\item[$\square$]
  \texttt{context.Context} as first parameter in all I/O and
  long-running functions
\item[$\square$]

\hypertarget{structs-are-not-classes}{%
\subsection{1. Structs Are Not Classes}\label{structs-are-not-classes}}

Go has no classes, no constructors, no inheritance. A struct is a value
type that holds named fields. Methods attach to types, not classes.

\begin{lstlisting}[language=Go]
\KeywordTok{type}\NormalTok{ Worker }\KeywordTok{struct} \OperatorTok{\{}
\NormalTok{    ID       }\DataTypeTok{string}
\NormalTok{    Endpoint }\DataTypeTok{string}
\NormalTok{    Timeout  time}\OperatorTok{.}\NormalTok{Duration}
\NormalTok{    client   }\OperatorTok{*}\NormalTok{http}\OperatorTok{.}\NormalTok{Client }\CommentTok{// unexported — internal state}
\OperatorTok{\}}
\end{lstlisting}

\textbf{Exported fields} (uppercase) are part of the public API ---
JSON-serializable, accessible outside the package.\\
\textbf{Unexported fields} (lowercase) are private --- cannot be
accessed outside the package. This is the encapsulation boundary in Go.

The ``constructor'' pattern is a function, by convention
\texttt{NewXxx}:

\begin{lstlisting}[language=Go]
\KeywordTok{func}\NormalTok{ NewWorker}\OperatorTok{(}\NormalTok{id}\OperatorTok{,}\NormalTok{ endpoint }\DataTypeTok{string}\OperatorTok{,}\NormalTok{ timeout time}\OperatorTok{.}\NormalTok{Duration}\OperatorTok{)} \OperatorTok{(*}\NormalTok{Worker}\OperatorTok{,} \DataTypeTok{error}\OperatorTok{)} \OperatorTok{\{}
    \ControlFlowTok{if}\NormalTok{ endpoint }\OperatorTok{==} \StringTok{""} \OperatorTok{\{}
        \ControlFlowTok{return} \OtherTok{nil}\OperatorTok{,}\NormalTok{ fmt}\OperatorTok{.}\NormalTok{Errorf}\OperatorTok{(}\StringTok{"worker \%s: endpoint must not be empty"}\OperatorTok{,}\NormalTok{ id}\OperatorTok{)}
    \OperatorTok{\}}
    \ControlFlowTok{return} \OperatorTok{\&}\NormalTok{Worker}\OperatorTok{\{}
\NormalTok{        ID}\OperatorTok{:}\NormalTok{       id}\OperatorTok{,}
\NormalTok{        Endpoint}\OperatorTok{:}\NormalTok{ endpoint}\OperatorTok{,}
\NormalTok{        Timeout}\OperatorTok{:}\NormalTok{  timeout}\OperatorTok{,}
\NormalTok{        client}\OperatorTok{:} \OperatorTok{\&}\NormalTok{http}\OperatorTok{.}\NormalTok{Client}\OperatorTok{\{}
\NormalTok{            Timeout}\OperatorTok{:}\NormalTok{ timeout}\OperatorTok{,}
\NormalTok{            Transport}\OperatorTok{:} \OperatorTok{\&}\NormalTok{http}\OperatorTok{.}\NormalTok{Transport}\OperatorTok{\{}
\NormalTok{                MaxIdleConnsPerHost}\OperatorTok{:} \DecValTok{100}\OperatorTok{,}
            \OperatorTok{\},}
        \OperatorTok{\},}
    \OperatorTok{\},} \OtherTok{nil}
\OperatorTok{\}}
\end{lstlisting}

Validation at construction time prevents invalid objects from ever
existing. This is the same principle as invariant preservation in C++,
but explicit rather than enforced via \texttt{private} constructors.

\hypertarget{value-vs-pointer-receivers}{%
\subsubsection{Value vs Pointer
Receivers}\label{value-vs-pointer-receivers}}

\begin{lstlisting}[language=Go]
\CommentTok{// Value receiver — operates on a copy; safe for reads, useless for mutation}
\KeywordTok{func} \OperatorTok{(}\NormalTok{w Worker}\OperatorTok{)}\NormalTok{ String}\OperatorTok{()} \DataTypeTok{string} \OperatorTok{\{}
    \ControlFlowTok{return}\NormalTok{ fmt}\OperatorTok{.}\NormalTok{Sprintf}\OperatorTok{(}\StringTok{"Worker(\%s @ \%s)"}\OperatorTok{,}\NormalTok{ w}\OperatorTok{.}\NormalTok{ID}\OperatorTok{,}\NormalTok{ w}\OperatorTok{.}\NormalTok{Endpoint}\OperatorTok{)}
\OperatorTok{\}}

\CommentTok{// Pointer receiver — operates on the original; required for mutation or large structs}
\KeywordTok{func} \OperatorTok{(}\NormalTok{w }\OperatorTok{*}\NormalTok{Worker}\OperatorTok{)}\NormalTok{ SetTimeout}\OperatorTok{(}\NormalTok{d time}\OperatorTok{.}\NormalTok{Duration}\OperatorTok{)} \OperatorTok{\{}
\NormalTok{    w}\OperatorTok{.}\NormalTok{Timeout }\OperatorTok{=}\NormalTok{ d}
\NormalTok{    w}\OperatorTok{.}\NormalTok{client}\OperatorTok{.}\NormalTok{Timeout }\OperatorTok{=}\NormalTok{ d}
\OperatorTok{\}}
\end{lstlisting}

\textbf{Rule of thumb for distributed systems:} - Large structs → always
pointer receiver - Structs with internal state that must mutate
(mutexes, channels) → always pointer receiver - Small value types
(coordinates, time ranges, metric values) → value receiver is fine

A struct with a \texttt{sync.Mutex} field \textbf{must always} use
pointer receivers. Copying a mutex by value breaks its semantics
silently.

\hypertarget{interfaces-structural-typing-and-inversion-of-control}{%
\subsection{2. Interfaces --- Structural Typing and Inversion of
Control}\label{interfaces-structural-typing-and-inversion-of-control}}

An interface in Go is a set of method signatures. Any type that has
those methods satisfies the interface --- with zero explicit
declaration.

\begin{lstlisting}[language=Go]
\CommentTok{// Defined in internal/store/ — the consumption site}
\KeywordTok{type}\NormalTok{ MetricStore }\KeywordTok{interface} \OperatorTok{\{}
\NormalTok{    Save}\OperatorTok{(}\NormalTok{ctx context}\OperatorTok{.}\NormalTok{Context}\OperatorTok{,}\NormalTok{ m Metric}\OperatorTok{)} \DataTypeTok{error}
\NormalTok{    GetByRunID}\OperatorTok{(}\NormalTok{ctx context}\OperatorTok{.}\NormalTok{Context}\OperatorTok{,}\NormalTok{ runID }\DataTypeTok{string}\OperatorTok{)} \OperatorTok{([]}\NormalTok{Metric}\OperatorTok{,} \DataTypeTok{error}\OperatorTok{)}
\OperatorTok{\}}
\end{lstlisting}

\begin{lstlisting}[language=Go]
\CommentTok{// internal/store/postgres.go — satisfies MetricStore implicitly}
\KeywordTok{type}\NormalTok{ PostgresStore }\KeywordTok{struct}\OperatorTok{\{}\NormalTok{ db }\OperatorTok{*}\NormalTok{sql}\OperatorTok{.}\NormalTok{DB }\OperatorTok{\}}

\KeywordTok{func} \OperatorTok{(}\NormalTok{s }\OperatorTok{*}\NormalTok{PostgresStore}\OperatorTok{)}\NormalTok{ Save}\OperatorTok{(}\NormalTok{ctx context}\OperatorTok{.}\NormalTok{Context}\OperatorTok{,}\NormalTok{ m Metric}\OperatorTok{)} \DataTypeTok{error}        \OperatorTok{\{} \CommentTok{/* ... */} \OperatorTok{\}}
\KeywordTok{func} \OperatorTok{(}\NormalTok{s }\OperatorTok{*}\NormalTok{PostgresStore}\OperatorTok{)}\NormalTok{ GetByRunID}\OperatorTok{(}\NormalTok{ctx context}\OperatorTok{.}\NormalTok{Context}\OperatorTok{,}\NormalTok{ runID }\DataTypeTok{string}\OperatorTok{)} \OperatorTok{([]}\NormalTok{Metric}\OperatorTok{,} \DataTypeTok{error}\OperatorTok{)} \OperatorTok{\{} \CommentTok{/* ... */} \OperatorTok{\}}

\CommentTok{// internal/store/memory.go — also satisfies MetricStore}
\KeywordTok{type}\NormalTok{ MemoryStore }\KeywordTok{struct} \OperatorTok{\{}
\NormalTok{    mu   sync}\OperatorTok{.}\NormalTok{RWMutex}
\NormalTok{    data }\KeywordTok{map}\OperatorTok{[}\DataTypeTok{string}\OperatorTok{][]}\NormalTok{Metric}
\OperatorTok{\}}

\KeywordTok{func} \OperatorTok{(}\NormalTok{s }\OperatorTok{*}\NormalTok{MemoryStore}\OperatorTok{)}\NormalTok{ Save}\OperatorTok{(}\NormalTok{\_ context}\OperatorTok{.}\NormalTok{Context}\OperatorTok{,}\NormalTok{ m Metric}\OperatorTok{)} \DataTypeTok{error}            \OperatorTok{\{} \CommentTok{/* ... */} \OperatorTok{\}}
\KeywordTok{func} \OperatorTok{(}\NormalTok{s }\OperatorTok{*}\NormalTok{MemoryStore}\OperatorTok{)}\NormalTok{ GetByRunID}\OperatorTok{(}\NormalTok{\_ context}\OperatorTok{.}\NormalTok{Context}\OperatorTok{,}\NormalTok{ runID }\DataTypeTok{string}\OperatorTok{)} \OperatorTok{([]}\NormalTok{Metric}\OperatorTok{,} \DataTypeTok{error}\OperatorTok{)} \OperatorTok{\{} \CommentTok{/* ... */} \OperatorTok{\}}

The \texttt{PostgresStore} and \texttt{MemoryStore} types know nothing

code that \emph{uses} the store, not the code that \emph{implements} it.
This is Dependency Inversion in action --- and it is the architectural
key to testability in Go.

\hypertarget{interfaces-at-the-consumption-site}{%
\subsubsection{2.1 Interfaces at the Consumption
Site}\label{interfaces-at-the-consumption-site}}

Contrast Go with Java:

\begin{lstlisting}[language=Go]
\CommentTok{// Java: interface defined at the provider side, explicitly implemented}
\KeywordTok{public} \KeywordTok{interface}\NormalTok{ MetricStore }\OperatorTok{\{} \KeywordTok{...} \OperatorTok{\}}
\KeywordTok{public} \KeywordTok{class}\NormalTok{ PostgresStore }\KeywordTok{implements}\NormalTok{ MetricStore }\OperatorTok{\{} \KeywordTok{...} \OperatorTok{\}}
\end{lstlisting}

\begin{lstlisting}[language=Go]
\CommentTok{// Go: interface defined at the consumer side, implicitly satisfied}
\CommentTok{// In the package that USES the store:}
\KeywordTok{type}\NormalTok{ MetricStore }\KeywordTok{interface} \OperatorTok{\{}\NormalTok{ Save}\OperatorTok{(...)} \DataTypeTok{error} \OperatorTok{\}}

\CommentTok{// In main.go: the concrete type flows in}
\KeywordTok{var}\NormalTok{ store MetricStore }\OperatorTok{=}\NormalTok{ postgres}\OperatorTok{.}\NormalTok{NewStore}\OperatorTok{(}\NormalTok{db}\OperatorTok{)}
\end{lstlisting}

This means you can define your own interface for a third-party library
type and wrap it for testing --- without modifying the library.

\hypertarget{interface-sizing-keep-them-small}{%
\subsubsection{2.2 Interface Sizing --- Keep Them
Small}\label{interface-sizing-keep-them-small}}

The Go standard library uses the rule of thumb: \textbf{the bigger the
interface, the weaker the abstraction}.

\begin{lstlisting}[language=Go]
\CommentTok{// io.Reader — one method; used EVERYWHERE}
\KeywordTok{type}\NormalTok{ Reader }\KeywordTok{interface} \OperatorTok{\{}
\NormalTok{    Read}\OperatorTok{(}\NormalTok{p }\OperatorTok{[]}\DataTypeTok{byte}\OperatorTok{)} \OperatorTok{(}\NormalTok{n }\DataTypeTok{int}\OperatorTok{,}\NormalTok{ err }\DataTypeTok{error}\OperatorTok{)}

\CommentTok{// io.Writer — one method; composable with Reader}
\KeywordTok{type}\NormalTok{ Writer }\KeywordTok{interface} \OperatorTok{\{}
\NormalTok{    Write}\OperatorTok{(}\NormalTok{p }\OperatorTok{[]}\DataTypeTok{byte}\OperatorTok{)} \OperatorTok{(}\NormalTok{n }\DataTypeTok{int}\OperatorTok{,}\NormalTok{ err }\DataTypeTok{error}\OperatorTok{)}
\OperatorTok{\}}

\CommentTok{// io.ReadWriter — composed from both}
\KeywordTok{type}\NormalTok{ ReadWriter }\KeywordTok{interface} \OperatorTok{\{}
\NormalTok{    Reader}
\NormalTok{    Writer}
\OperatorTok{\}}
\end{lstlisting}

\begin{lstlisting}[language=Go]
\CommentTok{// Too broad — forces implementers to do too much}

\OperatorTok{\}}

\CommentTok{// Better — focused contracts that can be composed}

\NormalTok{    Save}\OperatorTok{(}\NormalTok{ctx context}\OperatorTok{.}\NormalTok{Context}\OperatorTok{,}\NormalTok{ m Metric}\OperatorTok{)} \DataTypeTok{error}
\OperatorTok{\}}

\KeywordTok{type}\NormalTok{ MetricQuerier }\KeywordTok{interface} \OperatorTok{\{}

\OperatorTok{\}}
\end{lstlisting}

\begin{lstlisting}[language=Go]

    \ControlFlowTok{return}\NormalTok{ b}\OperatorTok{.}\NormalTok{running}
\OperatorTok{\}}

\KeywordTok{func} \OperatorTok{(}\NormalTok{b }\OperatorTok{*}\NormalTok{BaseWorker}\OperatorTok{)}\NormalTok{ Start}\OperatorTok{()} \OperatorTok{\{}
\NormalTok{    b}\OperatorTok{.}\NormalTok{mu}\OperatorTok{.}\NormalTok{Lock}\OperatorTok{()}

\OperatorTok{\}}

\hypertarget{key-takeaways-2}{%
\subsection{Key Takeaways}\label{key-takeaways-2}}

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  \textbf{Structs are value types with methods.} Use pointer receivers
  for mutation and large structs.
\item
  \textbf{Interfaces are implicit and owned by consumers.} Define them
  at the usage site, keep them narrow.
\item
  \textbf{Embedding is composition, not inheritance.} Promotes fields
  and methods without coupling.
\item
  \textbf{The decorator pattern} (wrapping interfaces) is how you add
  logging, metrics, and circuit breaking without modifying existing
  code.
\item
  \textbf{\texttt{sync.Mutex} + value copying} is the safe pattern for
  concurrent struct access.
\item
  \textbf{\texttt{sync.Pool}} reduces allocation pressure in
  high-throughput hot paths.
\end{enumerate}

\hypertarget{why-go-chose-error-values-over-exceptions}{%
\subsection{1. Why Go Chose Error Values Over
Exceptions}\label{why-go-chose-error-values-over-exceptions}}

In Java and C++, exceptions break the normal control flow. A
\texttt{throw} in a Kafka consumer deep in a call stack can unwind all
the way to a top-level \texttt{catch} that loses all context about what
actually failed. You get a stack trace --- useful for debugging locally,
useless for structured log analysis in production.

Go's designers made a deliberate trade: \textbf{errors are values,
returned in-band, handled at every call site}. The consequence is
verbosity. The benefit is that every failure path is visible, testable,
and composable.

\begin{lstlisting}[language=Go]
\CommentTok{// Java mental model — exception can silently propagate through layers}
\NormalTok{public void consumeEvent}\OperatorTok{(}\NormalTok{KafkaRecord record}\OperatorTok{)} \OperatorTok{\{}
\NormalTok{    MetricEvent event }\OperatorTok{=}\NormalTok{ parser}\OperatorTok{.}\NormalTok{parse}\OperatorTok{(}\NormalTok{record}\OperatorTok{.}\NormalTok{value}\OperatorTok{());} \CommentTok{// throws ParseException}
\NormalTok{    store}\OperatorTok{.}\NormalTok{save}\OperatorTok{(}\NormalTok{event}\OperatorTok{);}                                 \CommentTok{// throws SQLException}
    \CommentTok{// nothing here catches — unwinds to caller}
\OperatorTok{\}}

\CommentTok{// Go mental model — every error is a decision point}
\KeywordTok{func}\NormalTok{ consumeEvent}\OperatorTok{(}\NormalTok{record kafka}\OperatorTok{.}\NormalTok{Message}\OperatorTok{)} \DataTypeTok{error} \OperatorTok{\{}
\NormalTok{    event}\OperatorTok{,}\NormalTok{ err }\OperatorTok{:=}\NormalTok{ parseEvent}\OperatorTok{(}\NormalTok{record}\OperatorTok{.}\NormalTok{Value}\OperatorTok{)}
    \ControlFlowTok{if}\NormalTok{ err }\OperatorTok{!=} \OtherTok{nil} \OperatorTok{\{}
        \ControlFlowTok{return}\NormalTok{ fmt}\OperatorTok{.}\NormalTok{Errorf}\OperatorTok{(}\StringTok{"parse event at offset \%d: \%w"}\OperatorTok{,}\NormalTok{ record}\OperatorTok{.}\NormalTok{Offset}\OperatorTok{,}\NormalTok{ err}\OperatorTok{)}
    \OperatorTok{\}}
    \ControlFlowTok{if}\NormalTok{ err }\OperatorTok{:=}\NormalTok{ store}\OperatorTok{.}\NormalTok{Save}\OperatorTok{(}\NormalTok{ctx}\OperatorTok{,}\NormalTok{ event}\OperatorTok{);}\NormalTok{ err }\OperatorTok{!=} \OtherTok{nil} \OperatorTok{\{}
        \ControlFlowTok{return}\NormalTok{ fmt}\OperatorTok{.}\NormalTok{Errorf}\OperatorTok{(}\StringTok{"save event \%s: \%w"}\OperatorTok{,}\NormalTok{ event}\OperatorTok{.}\NormalTok{ID}\OperatorTok{,}\NormalTok{ err}\OperatorTok{)}
    \OperatorTok{\}}
    \ControlFlowTok{return} \OtherTok{nil}
\OperatorTok{\}}
\end{lstlisting}

The error from \texttt{consumeEvent} carries full context: what failed,
where, and the original cause --- all as a string that appears in your
structured logs with zero stack trace parsing.

\hypertarget{the-error-interface}{%
\subsection{\texorpdfstring{2. The \texttt{error}
Interface}{2. The error Interface}}\label{the-error-interface}}

\texttt{error} is a built-in interface with a single method:

\begin{lstlisting}[language=Go]
\KeywordTok{type} \DataTypeTok{error} \KeywordTok{interface} \OperatorTok{\{}
\NormalTok{    Error}\OperatorTok{()} \DataTypeTok{string}
\OperatorTok{\}}
\end{lstlisting}

Any type with an \texttt{Error()\ string} method satisfies it. This
simplicity is intentional --- errors can carry arbitrary data, not just
strings.

\hypertarget{sentinel-errors}{%
\subsubsection{2.1 Sentinel Errors}\label{sentinel-errors}}

Sentinel errors are package-level variables representing known, expected
error conditions:

\begin{lstlisting}[language=Go]
\KeywordTok{package}\NormalTok{ store}

\KeywordTok{import} \StringTok{"errors"}

\KeywordTok{var} \OperatorTok{(}
\NormalTok{    ErrNotFound      }\OperatorTok{=}\NormalTok{ errors}\OperatorTok{.}\NormalTok{New}\OperatorTok{(}\StringTok{"record not found"}\OperatorTok{)}
\NormalTok{    ErrAlreadyExists }\OperatorTok{=}\NormalTok{ errors}\OperatorTok{.}\NormalTok{New}\OperatorTok{(}\StringTok{"record already exists"}\OperatorTok{)}
\NormalTok{    ErrInvalidInput  }\OperatorTok{=}\NormalTok{ errors}\OperatorTok{.}\NormalTok{New}\OperatorTok{(}\StringTok{"invalid input"}\OperatorTok{)}
\OperatorTok{)}
\end{lstlisting}

Callers check for them using \texttt{errors.Is()}:

\begin{lstlisting}[language=Go]
\NormalTok{metric}\OperatorTok{,}\NormalTok{ err }\OperatorTok{:=}\NormalTok{ store}\OperatorTok{.}\NormalTok{GetByRunID}\OperatorTok{(}\NormalTok{ctx}\OperatorTok{,}\NormalTok{ runID}\OperatorTok{)}
\ControlFlowTok{if}\NormalTok{ errors}\OperatorTok{.}\NormalTok{Is}\OperatorTok{(}\NormalTok{err}\OperatorTok{,}\NormalTok{ store}\OperatorTok{.}\NormalTok{ErrNotFound}\OperatorTok{)} \OperatorTok{\{}
\NormalTok{    http}\OperatorTok{.}\NormalTok{Error}\OperatorTok{(}\NormalTok{w}\OperatorTok{,} \StringTok{"run not found"}\OperatorTok{,}\NormalTok{ http}\OperatorTok{.}\NormalTok{StatusNotFound}\OperatorTok{)}
    \ControlFlowTok{return}
\OperatorTok{\}}
\ControlFlowTok{if}\NormalTok{ err }\OperatorTok{!=} \OtherTok{nil} \OperatorTok{\{}
\NormalTok{    http}\OperatorTok{.}\NormalTok{Error}\OperatorTok{(}\NormalTok{w}\OperatorTok{,} \StringTok{"internal error"}\OperatorTok{,}\NormalTok{ http}\OperatorTok{.}\NormalTok{StatusInternalServerError}\OperatorTok{)}

\OperatorTok{\}}
\end{lstlisting}

\textbf{Rule:} Use sentinel errors for conditions the caller is expected
to handle differently. Don't create a sentinel for every possible
failure.

\hypertarget{error-wrapping-with-w}{%
\subsection{\texorpdfstring{3. Error Wrapping with
\texttt{\%w}}{3. Error Wrapping with \%w}}\label{error-wrapping-with-w}}

\texttt{fmt.Errorf} with the \texttt{\%w} verb wraps an error,
preserving it in a chain:

\begin{lstlisting}[language=Go]
\KeywordTok{func}\NormalTok{ processKafkaEvent}\OperatorTok{(}\NormalTok{msg kafka}\OperatorTok{.}\NormalTok{Message}\OperatorTok{)} \DataTypeTok{error} \OperatorTok{\{}
\NormalTok{    event}\OperatorTok{,}\NormalTok{ err }\OperatorTok{:=}\NormalTok{ parseEvent}\OperatorTok{(}\NormalTok{msg}\OperatorTok{.}\NormalTok{Value}\OperatorTok{)}
    \ControlFlowTok{if}\NormalTok{ err }\OperatorTok{!=} \OtherTok{nil} \OperatorTok{\{}
        \CommentTok{// Wrap with context — original error is preserved}
        \ControlFlowTok{return}\NormalTok{ fmt}\OperatorTok{.}\NormalTok{Errorf}\OperatorTok{(}\StringTok{"offset \%d topic \%s: \%w"}\OperatorTok{,}\NormalTok{ msg}\OperatorTok{.}\NormalTok{Offset}\OperatorTok{,}\NormalTok{ msg}\OperatorTok{.}\NormalTok{Topic}\OperatorTok{,}\NormalTok{ err}\OperatorTok{)}
    \OperatorTok{\}}
    \ControlFlowTok{return} \OtherTok{nil}
\OperatorTok{\}}
\end{lstlisting}

The resulting error message:
\texttt{"offset\ 1042\ topic\ archer.metrics:\ json:\ cannot\ unmarshal\ string\ into\ Go\ value\ of\ type\ float64"}

The chain:

\begin{verbatim}
fmt.Errorf wrapper → json.UnmarshalTypeError (original)
\end{verbatim}

\texttt{errors.Is(err,\ target)} and \texttt{errors.As(err,\ \&target)}
traverse this chain automatically.

\hypertarget{when-not-to-wrap}{%
\subsubsection{3.1 When NOT to Wrap}\label{when-not-to-wrap}}

Not every error needs wrapping. Wrapping adds a new string layer. Only
wrap when you add meaningful context:

\begin{lstlisting}[language=Go]
\CommentTok{// GOOD — adds context about what operation failed and with what input}
\ControlFlowTok{return}\NormalTok{ fmt}\OperatorTok{.}\NormalTok{Errorf}\OperatorTok{(}\StringTok{"store metric for run \%s: \%w"}\OperatorTok{,}\NormalTok{ runID}\OperatorTok{,}\NormalTok{ err}\OperatorTok{)}

\CommentTok{// REDUNDANT — just repeats what the error already says}
\ControlFlowTok{return}\NormalTok{ fmt}\OperatorTok{.}\NormalTok{Errorf}\OperatorTok{(}\StringTok{"error: \%w"}\OperatorTok{,}\NormalTok{ err}\OperatorTok{)}

\CommentTok{// GOOD — sentinel error, no wrapping needed}
\ControlFlowTok{return}\NormalTok{ store}\OperatorTok{.}\NormalTok{ErrNotFound}
\end{lstlisting}

on a non-nil interface. They are not the Go equivalent of exceptions.

middleware:

\hypertarget{key-takeaways-3}{%
\subsection{Key Takeaways}\label{key-takeaways-3}}

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  \textbf{Errors are values} --- returned in-band, handled explicitly at
  every call site.
\item
  \textbf{\texttt{\%w} wraps errors} --- preserving them for
  \texttt{errors.Is} and \texttt{errors.As} traversal.
\item
  \textbf{Sentinel errors} for known conditions, \textbf{typed errors}
  for structured data.
\item
  \textbf{\texttt{context.Canceled} is not an error} --- it is a
  shutdown signal. Always check \texttt{ctx.Err()} first.
\item
  \textbf{\texttt{errgroup}} for concurrent fan-out where one failure
  should abort the rest.
\item
  \textbf{Recover in long-running goroutines} --- panics crash the
  process.
\item
  \textbf{Structure your error logs} --- trace ID, operation,
  parameters. Never bare \texttt{log.Printf}.
\end{enumerate}

\subsection{What Actually Matters for the
Hackathon}\label{what-actually-matters-for-the-hackathon-3}}

\begin{itemize}
\tightlist
\item
  Never swallow an error with \texttt{\_} in backend code unless you
  explicitly document why
\item
  The \texttt{writeError} helper pattern eliminates 80\% of HTTP handler
  boilerplate
\item
  \texttt{errgroup} is the right tool whenever you spawn N goroutines
  and need the first error
\item
  Check \texttt{context.Canceled} first in every I/O loop --- critical
  for clean SIGTERM handling
\end{itemize}
